# Rebuilding the chat, admin and backend

Everything in this document is site agnostic. The marketing copy and the
photographs are the only parts specific to Lifewell; the messaging, dashboard
and email plumbing transfer to any site unchanged.

Two halves:

1. **[The technical setup](#the-technical-setup)** describes what exists and
   why each decision was made.
2. **[The rebuild prompt](#the-rebuild-prompt)** is a single block to paste
   into a fresh Claude Code session to produce the same thing.

---

## The technical setup

### Stack

| Layer | Choice | Notes |
| --- | --- | --- |
| Framework | TanStack Start 1.168 (SSR) + TanStack Router 1.170 | File based routes, `routeTree.gen.ts` is generated by the router vite plugin |
| Build | Vite 8 + nitro, preset `vercel` | Writes `.vercel/output/` (Build Output API v3), so no routing config is needed |
| Database, auth, realtime | Supabase (free tier is enough) | Postgres + row level security + `postgres_changes` realtime |
| Email | Resend | Outbound sends and, optionally, inbound mail via a Svix signed webhook |
| Styling | Tailwind v4 (`@utility` blocks in `src/styles.css`, no config file) | |
| Validation | Zod 3 | Every server function validates its input |
| Host | Vercel, building the repository's default branch | |

### The three write paths, and why they differ

This is the core of the design. There are exactly three ways data enters the
database, and each one has a different trust model.

```
                        ┌─────────────────────────────────────────┐
  Contact form  ───────▶│ submitForm  (createServerFn, POST)      │
  Booking form  ───────▶│  • zod validation + honeypot            │
                        │  • writes with the SERVICE ROLE key     │──▶ enquiries
                        │  • sends a notification through Resend  │──▶ bookings
                        └─────────────────────────────────────────┘

                        ┌─────────────────────────────────────────┐
  Chat widget   ───────▶│ Browser writes DIRECTLY under the       │──▶ chat_sessions
                        │ visitor's own anonymous auth session.   │──▶ chat_messages
                        │ RLS enforces "your own session only".   │
                        │ submitForm is called only to email the  │
                        │ staff notification.                     │
                        └─────────────────────────────────────────┘

                        ┌─────────────────────────────────────────┐
  Resend inbound ──────▶│ POST /api/inbound-email                 │──▶ email_threads
  webhook               │  • Svix HMAC over the RAW request bytes │──▶ email_messages
                        │  • writes with the service role         │
                        └─────────────────────────────────────────┘
```

**Forms never touch the database from the browser.** `enquiries` and `bookings`
have no anon policy at all. A leaked anon key cannot be used to stuff the
inbox, and the Resend key never reaches the client.

**Chat rows are written from the browser**, because RLS can express
"the session whose `visitor_id = auth.uid()`" precisely, and doing it in the
browser is what makes the widget feel instant. Visitors get a real `auth.uid()`
from `supabase.auth.signInAnonymously()`, so there is no bearer token scheme of
our own to get wrong.

**Reads are all RLS.** The dashboard queries Supabase directly with the staff
member's own session; the policies decide what comes back. There is no
"admin API" to keep in step with the policies.

### Schema

Two migrations, both guarded so they can be re-run after an edit rather than
erroring half way.

`supabase/migrations/0001_init.sql`

- `admins(user_id → auth.users, email)` plus a `SECURITY DEFINER is_admin()`.
  It has to be `SECURITY DEFINER`, otherwise a policy on `admins` that calls
  `is_admin()` recurses on `admins` itself.
- `item_status` enum: `new | in_progress | closed`.
- `enquiries` and `bookings`. Admin select and update only, no anon policy.
- `chat_sessions(visitor_id uuid default auth.uid(), visitor_name,
  visitor_email, last_message_at, status)`.
- `chat_messages(session_id, sender check in ('visitor','agent'), body)`.
- An `after insert` trigger on `chat_messages` that bumps `last_message_at`
  and, when the sender is the visitor, sets the session status back to `new`.
  A follow-up on a closed conversation therefore cannot be missed.
- `chat_sessions`, `chat_messages` and `bookings` are added to the
  `supabase_realtime` publication. Realtime honours RLS, so a visitor's
  subscription only ever delivers rows from their own session.

`supabase/migrations/0002_email.sql` (optional, only if you receive mail)

- `email_threads` keyed per correspondent, not per mailbox, with an index on
  `(lower(participant_email), lower(subject))` so a reply that carries no
  `In-Reply-To` header still lands on the right conversation.
- `email_messages` with `direction in ('inbound','outbound')`, the RFC 5322
  `message_id` and `in_reply_to`. A **unique partial index** on `message_id`
  makes redelivery idempotent, because inbound webhooks retry.
- The same touch trigger, driven by `direction` instead of `sender`.

`supabase/grant-admin.sql` is deliberately not part of the migration: the
migration cannot know your address. Create the login under Authentication →
Users (tick Auto Confirm User), edit the one marked line, run the file.

### Runtime configuration, not build time

This is the decision most likely to be got wrong on a rebuild.

The browser needs the Supabase project URL and anon key. Both are public; RLS
is what protects the data, not their secrecy. The obvious route is a `VITE_`
prefixed variable inlined at build time. That was tried and abandoned:

- Vercel refuses to mark a `VITE_` variable "Sensitive", because it knows the
  prefix is published.
- Vercel's Supabase integration injects its own un-prefixed names.
- Any change needs a rebuild. A build that ran before the variables existed
  produces a bundle that can never connect, with no signal until someone opens
  the chat.

So instead `loadPublicConfig` is a server function called from the **root
route's loader**. The values are serialised into the SSR payload, and
`RootComponent` calls `setPublicConfig()` during render, before any child
mounts. Setting a variable takes effect on the next request, not the next
build.

Three consequences worth knowing:

- `src/lib/supabase.ts` exports a **`Proxy`**, not a client. `createClient`
  throws on an empty URL and this module is in the SSR bundle, so constructing
  eagerly would fail to render every page rather than just losing the chat.
  The real client is built on first property access.
- `attachSupabaseAuth`, the global function middleware that puts the bearer
  token on server function calls, runs for **every** server function including
  `loadPublicConfig` itself. It must start with
  `if (!isSupabaseConfigured()) return next();` or it constructs a client with
  an empty URL and 500s the root loader, taking the whole app down.
- Every variable is read through a list of accepted spellings
  (`SUPABASE_URL`, `VITE_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_URL`, …), so
  connecting Vercel's Supabase integration is enough on its own.

### Auth

| Who | Mechanism |
| --- | --- |
| Visitor | `signInAnonymously()`. Real `auth.uid()`, so RLS grants them their own chat and nothing else. Requires Authentication → Providers → Anonymous to be enabled. |
| Staff, in the browser | `signInWithPassword()` at `/auth`, then `useAdminAuth` queries the `admins` table. Membership is a real query, not a token claim, so revoking someone is a row delete that takes effect on their next load. |
| Staff, server side | `requireAdmin(request)` validates the bearer token **with Supabase Auth** rather than decoding it locally, rejects `is_anonymous` users, then checks `admins` with the service role. |

`src/start.ts` registers `attachSupabaseAuth` as a global `functionMiddleware`
so the browser attaches `Authorization: Bearer …` to server function calls.
Defining `src/start.ts` at all opts out of Start's automatic CSRF middleware,
so it is re-added explicitly.

### Realtime

Both sides subscribe to `postgres_changes`.

- Visitor: one channel per session, filtered `session_id=eq.${sessionId}`.
- Dashboard: one channel on the whole table, refreshing the list and appending
  to the open thread.

Inserts are done with `.select().single()` so the row appears immediately
rather than waiting for the realtime echo, and the subscription handler
dedupes by `id`. That is what stops a double bubble.

### Email

Outbound is a plain `fetch` to `https://api.resend.com/emails`. `sendEmail`
returns `null` instead of throwing when `RESEND_API_KEY` is unset, and callers
decide whether that is fatal. For form notifications it is not: the row is
already stored and the dashboard is the source of truth.

Inbound is optional. Resend Inbound holds the MX records and posts an
`email.received` webhook. The handler reads the body as **raw text**, because
the Svix signature covers `id.timestamp.rawBody` and parsing to JSON first
then re-serialising changes key order and whitespace, so the HMAC no longer
matches.

### Why `/api/*` is dispatched by hand

This version of TanStack Start has no file based server routes. Anything an
outside service calls directly needs a plain HTTP endpoint, so `src/server.ts`
holds a small route table checked ahead of SSR:

```ts
const apiRoutes = {
  "/api/inbound-email": () => import("./lib/api/inbound-email.server").then(m => m.handleInboundEmail),
  "/api/health":        () => import("./lib/api/health.server").then(m => m.handleHealthCheck),
};
```

Everything the browser calls goes through `createServerFn` and never reaches
this table. `src/server.ts` is wired in through
`tanstackStart: { server: { entry: "server" } }` in `vite.config.ts`.

It also normalises h3's swallowed errors. h3 turns an in-handler throw into a
normal 500 whose body is `{"unhandled":true,"message":"HTTPError"}`, which a
`try/catch` never sees, so the response is inspected and swapped for a real
error page.

### Environment variables

Required:

| Purpose | Accepted names | Visibility |
| --- | --- | --- |
| Project URL | `SUPABASE_URL`, `VITE_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_URL` | Public |
| Anon key | `SUPABASE_ANON_KEY`, `VITE_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_PUBLISHABLE_KEY` | Public |
| Service role | `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_SECRET_KEY` | **Secret** |

Optional, all mail related: `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET`,
`MAIL_DOMAIN`, `FORM_TO`, `FORM_FROM`, `MAILBOX_ADDRESS`, `FORWARD_TO`.

**Never** put a service-role key, database password or JWT secret behind a
`VITE_` or `NEXT_PUBLIC_` prefix. Those are published to every visitor.

`GET /api/health` reports which of these the running server can actually see,
so a misconfigured deploy is diagnosed without reading function logs.

## The rebuild prompt

Paste the whole block below into a fresh Claude Code session, in an empty repo
or on top of an existing marketing site.

> Build a visitor chat widget, a contact form and a staff dashboard on
> TanStack Start (SSR) with Supabase and Resend, deploying to Vercel.
>
> **Architecture rules, which drive everything else.**
>
> 1. Visitors authenticate with `supabase.auth.signInAnonymously()`. Every row
>    they create carries a real `auth.uid()`, so row level security grants them
>    their own chat and nothing else. Do not invent a token scheme. Never put a
>    service-role key in the browser.
> 2. Form submissions never touch the database from the browser. `enquiries`
>    and `bookings` get no anon policy at all; writes go through a server
>    function holding the service-role key, so a leaked anon key cannot stuff
>    the inbox.
> 3. Chat rows *are* written from the browser, under the visitor's own
>    session, because RLS can express "your own session" precisely. The server
>    function is used only to send the staff notification.
> 4. The browser's Supabase config is served at runtime from the root route's
>    loader, never inlined at build time behind a `VITE_` prefix. Accept
>    `SUPABASE_URL`, `VITE_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_URL` as
>    equivalent, and the same for the anon key, so connecting Vercel's Supabase
>    integration is enough on its own.
> 5. Never let a missing configuration fail silently. Render a message naming
>    what is unset and where to set it.
>
> **Schema.** Two guarded, re-runnable SQL migrations under
> `supabase/migrations/`.
>
> `0001_init.sql`:
> - `admins(user_id references auth.users on delete cascade, email)` and a
>   `SECURITY DEFINER` `is_admin()` function, so policies can call it without
>   recursing on `admins` itself.
> - An `item_status` enum: `new | in_progress | closed`.
> - `enquiries(name, company, email, phone, subject, scope, status, notes)`.
>   RLS: admin select and update only. No anon policy.
> - `bookings(patient_name, email, phone, service, preferred_date,
>   preferred_time, notes, status)` with its own `booking_status` enum. Same
>   policy shape.
> - `chat_sessions(visitor_id uuid not null default auth.uid(), visitor_name,
>   visitor_email, last_message_at, status)`.
> - `chat_messages(session_id references chat_sessions on delete cascade,
>   sender text check (sender in ('visitor','agent')), body text check
>   (length between 1 and 4000))`.
> - Policies: a visitor inserts and reads only rows whose session has
>   `visitor_id = auth.uid()`, and may post only as `'visitor'`; admins read
>   everything and may post only as `'agent'`.
> - An `after insert` trigger on `chat_messages` that bumps `last_message_at`
>   and sets the session status back to `new` when the sender is the visitor,
>   so a follow-up on a closed conversation is not missed. An agent reply
>   leaves the status alone.
> - Add `chat_sessions`, `chat_messages` and `bookings` to the
>   `supabase_realtime` publication, guarded by a `pg_publication_tables`
>   check so re-running is safe.
>
> `0002_email.sql` (optional, only needed to receive mail):
> - `email_threads(subject, participant_email, participant_name,
>   last_message_at, status)`, keyed per correspondent rather than per mailbox,
>   with an index on `(lower(participant_email), lower(subject))` so a reply
>   carrying no `In-Reply-To` header still finds its thread. Store the subject
>   already stripped of `Re:` and `Fwd:`.
> - `email_messages(thread_id, direction check in ('inbound','outbound'),
>   from_email, from_name, to_email, subject, body_text, body_html, message_id,
>   in_reply_to, has_attachments)`, with a **unique partial index on
>   `message_id` where it is not null**, because inbound webhooks retry and
>   filing the same mail twice would duplicate the conversation.
> - Admin-only read policies, no insert policy at all: everything is written
>   by the server route with the service role.
> - The same touch trigger, driven by `direction = 'inbound'`.
>
> Also write `supabase/grant-admin.sql`: a `do $$` block with a single
> `admin_email` variable to edit, that looks the address up in `auth.users`,
> raises a clear exception if the login does not exist yet, and inserts into
> `admins` on conflict do nothing.
>
> **Backend.** A server-only module `src/lib/api/_shared.server.ts` (the
> `.server.ts` suffix keeps it out of the browser bundle) exporting:
> - An `env(names: string[])` helper returning the first non-empty variable,
>   and the resolved `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SERVICE_ROLE_KEY`,
>   `RESEND_API_KEY` and mail addresses built from a single `MAIL_DOMAIN`.
> - `adminClient()`, a service-role Supabase client with
>   `auth: { persistSession: false }`.
> - `sendEmail(options)` posting to the Resend API, returning the message id or
>   `null` when no API key is set, rather than throwing. Support `replyTo` and
>   an `inReplyTo` that sets both `In-Reply-To` and `References`.
> - `requireAdmin(request)`, which validates the caller's bearer token by
>   calling Supabase Auth (not by decoding it locally), rejects anonymous
>   users, then checks `admins` with the service role.
> - `verifyResendWebhook(rawBody, headers)`: Svix HMAC-SHA256 over
>   `id.timestamp.rawBody`, accepting both the `svix-*` and `webhook-*` header
>   names, enforcing a 300 second window, comparing in constant time, and
>   returning a *reason* string on failure rather than a bare false.
> - Small helpers: `text(value, max)`, `isEmail`, `escapeHtml`, `json`,
>   `errorMessage`, `parseAddress`, `normaliseSubject`, `emailBody`.
>
> Then:
> - `submitForm`, a `createServerFn({ method: "POST" })` validated by a zod
>   discriminated union on `kind: 'enquiry' | 'booking' | 'chat'`. It writes
>   with the service role, honours a `website` honeypot field by returning
>   success without writing, and emails a notification. The `chat` kind only
>   notifies, because the widget writes its own rows.
> - `sendEmailReply`, admin only via `requireAdmin`, which sends through Resend
>   threaded onto the newest inbound `message_id`, records the outbound message
>   on the thread, and moves the thread to `in_progress`.
> - `handleInboundEmail(request)`: verify the signature over the raw body
>   first, ignore any event type other than `email.received`, dedupe on the
>   Resend email id, find or create the thread, insert the message.
> - `handleHealthCheck(request)`: report which variables the running server can
>   see, listing every accepted spelling of anything missing, and whether the
>   webhook secret decodes to a usable key.
>
> **Wiring.** This TanStack Start version has no file based server routes, so
> in `src/server.ts` keep a small `Record<string, () => Promise<handler>>`
> checked before handing off to `@tanstack/react-start/server-entry`, mapping
> `/api/inbound-email` and `/api/health`. Point Start at it with
> `tanstackStart: { server: { entry: "server" } }` in `vite.config.ts`, and set
> `nitro: { preset: "vercel" }`.
>
> In `src/start.ts` register a global `functionMiddleware` that attaches the
> Supabase bearer token to server function calls. It runs for *every* server
> function including the one that fetches the config, so guard it with
> `if (!isSupabaseConfigured()) return next();` before touching the client.
> Defining `src/start.ts` opts out of Start's automatic CSRF middleware, so
> re-add `createCsrfMiddleware({ filter: ctx => ctx.handlerType === "serverFn" })`
> explicitly.
>
> **Config delivery.** `src/lib/public-config.ts` exports a `loadPublicConfig`
> server function reading the URL and anon key from the accepted names, plus
> module-level `setPublicConfig` / `getPublicConfig` / `isSupabaseConfigured`.
> The root route calls it in `loader` and `setPublicConfig(...)` during render,
> before any child mounts. `src/lib/supabase.ts` exports a **`Proxy`** that
> builds the real client on first property access, because `createClient`
> throws on an empty URL and this module is in the SSR bundle.
>
> **Frontend.**
> - `useVisitorChat`: anonymous sign-in reusing an existing session, session id
>   in `localStorage`, rejoin on mount (and forget the stored id if the row is
>   gone), a realtime subscription filtered to that session, and inserts done
>   with `.select().single()` so the row appears immediately, deduped by id
>   against the realtime echo. Turn the raw "Anonymous sign-ins are disabled"
>   error into a message naming the exact dashboard setting to change.
> - `useAdminAuth`: tracks the Supabase user, ignores anonymous ones, and
>   queries the `admins` table rather than reading a token claim.
> - `useFormSubmit`: form state, submitting flag, success and error, calling
>   `submitForm` through `useServerFn`.
> - A floating chat widget rendered from the root route on public pages only
>   (hide it under `/admin` and `/auth`), with a name/email/message start form
>   and then a live thread.
> - `/auth` with email and password sign-in.
> - `/admin` as an auth gate rendering a login when signed out, a "not on the
>   admin list" notice when signed in but not an admin, and a tabbed shell
>   otherwise. Four tabs, each list-and-detail with realtime and a status
>   control: enquiries, live chat, email threads, bookings. Set
>   `robots: noindex` on all of them.
>
> **Verify before you finish.** Run a production build and a typecheck. Add a
> `supabase/verify.sql` that asserts every table, policy, trigger and
> publication membership exists, and a README covering: enabling anonymous
> sign-ins, running the migrations, running `grant-admin.sql`, the environment
> variable table with its visibility column, and the fact that Vercel deploys
> the repository's *default* branch.

### Traps worth pre-empting

- A bare `import "./x"` for its side effect is **tree-shaken away** when
  `package.json` has `"sideEffects": false`. Export a function and call it.
- The global function middleware runs for the config fetch itself. Guard it.
- Vercel deploys the repository's **default branch**. Pushing to `main` when
  the default is something else deploys nothing.
- `FORWARD_TO` on your own domain loops mail back into the inbound webhook
  until the sending quota is gone.
- A lockfile from a hosted builder can pin a **private registry** the deploy
  cannot authenticate to.
- Anonymous sign-ins must be enabled on the *same* Supabase project the
  deployment points at, which is not necessarily the one last opened in the
  dashboard. `/api/health` prints which URL is in use.
